# Life OS 七项功能优化任务实施计划

## 一、文档状态与执行边界

> [!note] 后续需求替代说明
> 2026-09-28 的生活节律调整已经替代本文原“任务三：睡眠时间与时长格式”的当前产品行为：独立睡眠模块和精确睡眠前端录入已移除，改为健康状态中的睡眠情况区间单选；旧字段只用于历史兼容与导出。本文其余内容作为当时七项优化的实施记录保留，不应据此恢复旧交互。

本文最初用于需求梳理、技术设计、实施排序和验收定义；用户于 2026-09-23 明确要求按本计划实施七项工作，现已作为实现与验收基线执行。业务 schema 保持 v5，不对用户数据库或既有备份执行迁移和重写。

规划基线为 Git 提交 `0892681`，当前自动化测试基线为 154 项。实施期间必须遵守项目级 `AGENTS.md`：所有测试、诊断、数据库迁移演练和冻结 EXE 自检使用独立临时 `--home`，不得修改、移动、清理或覆盖真实 `life-os-data/backups/`。

本轮七项需求组成一次 v0.1 后续功能增量，但不预先决定新版本号。实现、审计和发行验证分别保留可核验证据；提交与版本发布仍需用户批准。

## 二、现状核对与总体判断

以下结论来自当前代码与测试，是后续实施的起点：

1. 习惯目前只有逐日打卡和单日聚合，没有周、月、年统计接口或报表界面；生活节律也只有单日读取与保存。
2. 分类已经保存在 `categories` 表，并由 `POST /api/categories` 创建。用户反馈的“习惯分类创建后没有保存”与现有后端设计不一致，因此必须先按真实操作路径复现，重点检查弹窗打开、异步加载、创建后选中、关闭未保存习惯、刷新页面和重启应用等状态衔接，不能直接假设数据库丢失。
3. 习惯 `icon` 当前贯穿表单、API、模型、序列化和导出，但页面并未用它表达实际信息。
4. 睡眠原先同时记录起止时间并支持自动计算和手工修正；现按追加需求简化为前一日入睡时分与直接填写的小时、分钟时长。
5. 日记当前使用日期输入框切换，所有可选历史日期仍可编辑；没有日记专用的月度索引接口或月历。
6. 全部任务的操作按钮由状态动态追加，位置和行数不固定；“开始、完成、退回待办、重新打开、取消、编辑、上移、下移、归档”可能同时出现。
7. 财务流水同时保留 `description`（说明）和 `note`（备注），两者存在于表单、API、数据库、序列化和导出。
8. 当前 SQLite 索引已经覆盖习惯日志日期、习惯与日期唯一组合、健康日期、日记日期及财务流水常用条件；是否新增索引必须以查询计划和基准数据为依据。

## 三、统一产品规则

### 3.1 时间区间

周、月、年统计统一使用自然周期，而不是滚动天数：

- 周：周一至周日。
- 月：自然月第一日至最后一日。
- 年：1 月 1 日至 12 月 31 日。
- `anchor` 表示用户当前查看周期内的任意日期；服务端负责解析实际起止日期。
- 当前周期中的未来日期显示为空白，不计入完成率、平均值或有效天数。
- 所有日期以应用运行设备的本地日期为准，不进行云端时区转换。

### 3.2 缺失值与统计精度

缺失数据保持 `null` 或“未记录”，不得按零补齐，也不得自动插值。睡眠与运动在服务层继续使用整数分钟，体重和 1–5 分量表的平均值显示一位小数。百分比由服务层返回稳定数值，前端只负责格式化，避免不同页面产生不同计算结果。

### 3.3 数据兼容策略

本轮默认不删除 SQLite 列，不清空旧字段，不重写历史备份：

- 习惯图标从用户界面和新建/编辑请求中移除，但旧 `icon` 数据、API 兼容字段和导出列先保留。
- 财务备注从“记一笔”界面和新请求中移除，但旧 `note` 数据、API 兼容字段和导出列先保留；编辑旧流水时省略该字段，不把历史备注覆盖为空。
- 睡眠界面只保留入睡时分和小时、分钟时长；入睡日期固定解释为记录日前一天。旧醒来时间和手工标记列仅为数据库兼容保留，不再直接编辑。
- 新统计均从现有明细实时聚合，不建立可失真的缓存表或重复汇总表。

只有审计阶段确认兼容字段已经完全无用且用户另行批准，才考虑在未来版本执行破坏性删列。

## 四、任务一：习惯与生活节律统计报表

### 4.1 页面与交互

习惯页和生活节律页分别新增“统计”区域，统一提供“周／月／年”分段选择、上一周期、下一周期和“回到本期”。页面首次打开使用当前日期所在周期；切换周期时保留当前报表类型并显示明确的起止日期。

周报和月报以每日数据为横轴；年报以 12 个月为横轴，避免一次绘制 365 个拥挤点。图表应使用本地 SVG 或 Canvas，不引入 CDN；若现有无构建前端不适合新增大型图表依赖，首版使用 CSS 网格、进度条和小型 SVG 折线/柱形图完成。所有图形必须配有数值表或可读文本，不能成为唯一信息来源。

### 4.2 习惯统计定义

拟新增接口：

```text
GET /api/habits/statistics?period=week|month|year&anchor=YYYY-MM-DD
```

响应至少包含：

```json
{
  "period": "month",
  "anchor": "2026-09-23",
  "date_from": "2026-09-01",
  "date_to": "2026-09-30",
  "effective_date_to": "2026-09-23",
  "granularity": "day",
  "summary": {
    "tracked_habits": 4,
    "completed_logs": 37,
    "days_with_completion": 18
  },
  "series": [],
  "habits": []
}
```

统计规则如下：

- `completed_logs` 只统计 `status=true` 的打卡。
- `days_with_completion` 是至少完成一项习惯的不同日期数。
- 报表包含当前启用习惯，以及区间内存在日志的停用习惯，避免历史记录消失。
- 每项习惯返回完成天数、区间内最长连续天数和按日/按月序列。
- 当前启用习惯可以显示“日历坚持率”：完成天数除以从 `max(周期开始日, 习惯创建本地日期)` 到 `effective_date_to` 的自然日数。
- 停用习惯因为现有模型没有停用历史，不计算可能误导的完成率，只显示实际完成天数和序列；界面注明数据口径。
- 当前连续天数以 `effective_date_to` 为截止日；区间最长连续天数不跨越所选周期边界。

服务层使用一次区间查询读取习惯日志，再在内存中完成有限范围聚合；年报最多处理一年明细。禁止按天或按习惯循环访问数据库。若压力数据表明 Python 聚合成为瓶颈，再改为 SQLite `GROUP BY`，但 API 合同保持不变。

### 4.3 生活节律统计定义

拟新增接口：

```text
GET /api/health/statistics?period=week|month|year&anchor=YYYY-MM-DD
```

响应包含周期元数据、汇总和时间序列。汇总至少包括：

- 睡眠：有效记录天数、平均/最短/最长时长、平均睡眠质量。
- 体重：首个记录、最后记录、期间变化、最低值、最高值；不对缺失日期插值。
- 运动：累计分钟、平均分钟、存在运动的天数。
- 状态量表：精力和情绪的有效天数与平均值。
- 身体健康：记录天数及最近若干条非空文字，不对自由文本做自动评分。

周/月返回逐日序列；年报返回逐月平均或总量，并在每个桶中附 `recorded_days`。睡眠时长在 API 中仍以分钟返回，前端统一格式化为“X 小时 Y 分钟”。

### 4.4 验收与测试

- 空数据库、部分缺失、跨月周、闰年二月、当前周期未来日期均有确定结果。
- 年报只有 12 个桶，周报始终按周一至周日排列。
- 停用习惯的历史完成记录仍可见，但不显示伪精确完成率。
- 同一组明细在服务、API 和页面上的合计一致。
- 查询次数不随区间天数或习惯数量线性增加；压力数据下无 N+1 查询。
- 七套主题、窄屏、键盘操作与 reduced-motion 均可使用。

## 五、任务二：习惯分类、图标与编辑按钮

### 5.1 分类持久化缺陷处理

先建立可重复的验收路径，再修改实现：

1. 打开“新建习惯”，现场创建分类并选中。
2. 分别测试保存习惯、取消习惯、关闭弹窗三条路径。
3. 重新打开弹窗、刷新页面并重启应用，确认分类仍存在。
4. 使用 `GET /api/categories?scope=habit` 和隔离数据库直接查询，区分“后端未提交”和“前端列表未刷新”。
5. 模拟分类加载慢于弹窗打开、创建请求重复点击和同名冲突。

预期修复方向是让 `CategorySelect` 在习惯弹窗每次打开时重新同步分类，创建成功后以服务端返回值更新并选中，同时保持按钮禁用和错误状态。若复现证明后端事务存在问题，再修服务层；不得为了掩盖界面状态问题重复插入分类。

验收标准：分类一经显示“分类已创建”，即使不保存当前习惯，也应在刷新与重启后继续存在；同名分类不产生重复行。

### 5.2 移除习惯图标入口

从习惯模板移除“图标类型”，从前端移除 `ICON_LABELS`、表单读写和新请求中的 `icon`。习惯列表不再显示图标相关文本。后端兼容字段、数据库列与导出暂时保留，避免修改已有数据或旧客户端合同。

### 5.3 编辑按钮视觉

“清单设置”中的“编辑”按钮使用 `button-primary` 或等价的主题主色类，形成深色背景与 `--on-primary` 文字。七套主题只通过 Token 决定实际颜色，不增加硬编码深色；停用项的编辑按钮也保持相同语义。

### 5.4 验收与测试

- 新建分类跨弹窗、刷新和应用重启持续存在。
- 分类加载失败不会清空已经存在的选项或误报创建成功。
- 习惯表单和列表不再出现图标选择或图标标签。
- 旧习惯中的 `icon` 值未被批量清空，完整导出仍可保留旧值。
- 七套主题下“编辑”按钮均有足够对比度和可见焦点。

## 六、任务三：睡眠时间与时长格式

### 6.1 输入形式

“入睡时间”使用 `time`，只显示和编辑 `HH:MM`。记录日期作为睡眠归属日，入睡日期固定为记录日的前一天；前端按设备本地时区生成带偏移的完整时间戳。醒来时间不再由用户填写。

前端加载时从现有 ISO 时间戳提取原始本地时分；保存时使用记录日前一天、所填时分和本地时区重新组合时间戳。数据库格式和历史值不迁移。

### 6.2 时长形式

睡眠时长直接使用“小时”和“分钟”两个数值控件：小时 `0–24`，分钟 `0–59`，合并结果不得超过 1440 分钟。服务层仍保存 `sleep_duration_minutes`，并由入睡时间加时长推导兼容字段 `sleep_end`；统计接口也以分钟计算，避免引入浮点小时误差。

### 6.3 验收与测试

- 记录日为 9 月 18 日时，`23:30` 入睡按 9 月 17 日保存；填写 7 小时 30 分钟后，底层兼容结束时间推导为 9 月 18 日 07:00。
- 历史完整时间戳能无损显示为时分，再次保存后的睡眠时长保持一致。
- 非前一日时间戳、非法分钟、超过 24 小时和日期切换时未保存等边界有明确反馈。
- Today、Calendar 日期详情和统计报表统一使用小时+分钟格式。

## 七、任务四：日记月历与非今日只读

### 7.1 月度索引接口

拟新增接口：

```text
GET /api/journal/month/YYYY-MM
```

接口只返回该月存在日记的日期、更新时间和可选的短摘要，不批量返回完整正文：

```json
{
  "month": "2026-09",
  "entries": [
    {"date": "2026-09-18", "updated_at": "...", "excerpt": "..."}
  ]
}
```

查询使用 `journals.date` 的唯一索引一次完成。摘要在服务端按字符数截断并去除 Markdown 控制字符；若摘要规则引入歧义，首版可以只返回日期和更新时间。

### 7.2 页面布局

日记页新增月历，支持上一月、下一月和“回到今天”。有日记的日期显示记录标记，当前选中日期与系统今天采用不同形状或边框，不只依靠颜色。选择日期后更新 URL `?date=YYYY-MM-DD` 并加载该日日记。

- 今天：显示完整编辑器、格式工具、图片插入、自动保存和预览。
- 非今天：进入“只读回顾”模式，隐藏或禁用编辑工具与图片上传，正文通过 Markdown 预览完整呈现；若无记录则显示只读空状态。
- 任意已有日期仍允许导出 Markdown。
- 日期切换前必须完成或明确处理今天尚未保存的内容。

### 7.3 服务端写保护

只在界面禁用并不足以满足“不可修改”。`PUT /api/journal/<date>` 与 `POST /api/journal/<date>/assets` 应校验本地系统日期；目标不是今天时返回 `409 Conflict` 和稳定错误码。`GET` 正文、月度索引、附件读取和导出不受限制。

系统跨越午夜或窗口恢复焦点时，前端重新判断可编辑状态；即使页面状态过期，服务端仍是最终保护边界。已有历史和未来记录不删除，只转为只读。

### 7.4 验收与测试

- 月历正确处理月首空位、28–31 天、闰年、跨年切换和今天定位。
- 有日记日期的标记来自日记索引，不误用“当天存在其他生活数据”的通用标记。
- 过去与未来日期不能修改正文或上传图片；直接调用写接口同样被拒绝。
- 今天仍能自动保存、插入时间、使用三级标题、插图、预览和导出。
- 历史 Markdown 与图片能完整阅读和导出。

## 八、任务五：全部任务按钮重排

### 8.1 固定布局

“执行清单—全部任务”中的未归档任务使用固定三列、两行操作网格：

```text
第一排：完成／重新打开（深色） | 上移 | 下移
第二排：编辑（深色）           | 取消 | 归档
```

解释规则：

- 待办和进行中任务第一格显示“完成”；已完成或已取消任务显示“重新打开”，保留现有可逆操作。
- “开始”和“退回待办”不再作为清单快捷按钮；如需设置进行中或待办，仍可从“编辑”窗口中的状态字段完成。
- 已完成或已取消任务的“取消”按钮禁用，保持网格位置稳定并提供明确状态提示。
- 第一项、最后一项的上移或下移按钮禁用而不是消失，避免其他按钮跳位。
- 已归档列表项不使用六按钮矩阵，仅保留现有“恢复”操作。

“完成／重新打开”和“编辑”使用主题主色深色背景；其余使用次级或安静按钮。归档仍是可恢复的软归档，但应与普通排序操作保持足够区分。

### 8.2 响应式与验收

- 桌面端严格保持每行三个按钮；窄屏可维持三列缩小文字间距，极窄屏才降为两列，但操作顺序不变。
- 所有状态下主要按钮位置稳定，进行中请求禁用整组相关操作，失败后恢复。
- 排序边界、完成、取消、重新打开、编辑、归档和恢复的原有 API 行为不变。
- 七套主题下两个深色按钮不会与禁用、危险或完成状态混淆。

## 九、任务六：财务“记一笔”移除备注

从财务流水新建/编辑弹窗移除“备注”文本域，只保留最长 300 字的“说明”。前端创建和编辑请求不再发送 `note`，流水列表只把 `description` 作为说明展示。

为保护既有数据，本轮不删除 `finance_transactions.note`，API 继续兼容旧客户端传入或返回该字段，完整 CSV 导出也继续保留该列。编辑一条含旧备注的流水时，因为请求省略 `note`，服务层必须保留旧值，不得隐式清空。若未来需要彻底删除旧备注，应先提供导出和迁移说明并单独批准。

验收包括新建、编辑、收入、支出、转账、信用卡消费和还款路径；表单中只能看到“说明”，请求载荷不含 `note`，旧数据库内容与备份均不变化。

## 十、任务七：全项目检查、测试与优化

### 10.1 使用体验审计

逐页检查 Today、Calendar、Tasks、Habits、Health、Journal、Finance 和 Settings：

- 主流程是否能在最少必要操作内完成，按钮名称和位置是否一致。
- 加载、空数据、保存中、成功、失败、重试和离开保护是否完整。
- 弹窗焦点、Escape、键盘顺序、屏幕缩放和错误定位是否可靠。
- 1280px、768px、375px 与桌面窗口缩放下是否有溢出、空白或遮挡。
- 七套主题是否保持对比度、焦点、图标和财务语义一致。
- 今天、历史和未来日期的可编辑边界是否在各入口一致。

审计发现按“阻断／高／中／低”分级。只直接修复与本轮功能密切相关、风险明确且可测试的问题；范围较大的重构写入后续清单，不在验收尾声临时扩大修改面。

### 10.2 数据完整性审计

- 执行 `PRAGMA integrity_check`、外键检查和 schema 版本检查。
- 核对分类作用域与任务、习惯、财务引用文字的一致性。
- 核对软归档记录、停用账户、停用习惯和历史统计的可见规则。
- 检查日记附件是否存在孤儿文件或缺失引用，只报告问题，不自动删除用户文件。
- 验证旧 `icon`、财务 `note` 和睡眠完整时间戳在升级后仍可导出和恢复。
- 对任何必要迁移先在备份副本与临时运行时演练；不得对真实数据库做诊断性写入。

### 10.3 查询与计算审计

先建立代表性临时数据集和计时基线，再用 `EXPLAIN QUERY PLAN` 检查：

- 周/月/年习惯统计和节律统计是否使用日期索引并保持固定查询次数。
- 日记月度索引是否使用 `journals.date` 唯一索引。
- 月历聚合是否继续批量查询，没有逐日 N+1。
- 财务汇总当前会读取全部流水再由 Python 汇总，应评估改为 SQLite 条件聚合和分组查询；只有结果一致且性能收益明确时才替换。
- 任务与习惯排序是否可能产生长期重复 `sort_order`；若存在，设计事务内重排而不是不断扩大整数。
- 序列化、日期格式化和前端重复请求是否可合并或取消。

优化优先保证结果正确、查询次数稳定和代码可维护，不以微小耗时差异引入缓存表。所有金额继续使用整数分，睡眠与运动继续使用整数分钟。

### 10.4 测试与发布验证

至少补充以下测试：

- 统计服务与 API 的自然周期、缺失值、闰年、连续天数和聚合口径。
- 分类创建跨弹窗、刷新和重启的持久化回归。
- 睡眠时分输入、跨午夜、手动小时+分钟和历史数据兼容。
- 日记月度索引、今天写入、非今天写保护、历史阅读和导出。
- 任务六按钮布局、状态转换、边界禁用和响应式结构。
- 财务表单载荷无 `note`，编辑旧记录不会清空历史备注。
- 数据库初始化、完整导出、备份恢复、迁移和发行验收回归。

最终执行 Python 全量测试、JavaScript 语法检查、关键页面真实浏览器验收、七主题截图抽查、根目录与 `onedir` EXE 隔离自检。构建前后逐文件核对真实备份 SHA-256，变化数必须为 0。

## 十一、实施顺序与提交设计

建议按以下顺序执行：

1. **基线与复现**：记录 Git 状态、测试基线和真实备份只读哈希；复现习惯分类问题，建立压力数据脚本与界面检查表。
2. **领域与 API**：完成统计区间解析、习惯/健康统计、日记月度索引与非今天写保护，并先通过服务/API 测试。
3. **独立小改动**：完成习惯分类同步、移除图标入口、睡眠格式、任务按钮矩阵和财务备注入口移除。
4. **统计与日记界面**：接入报表、周期导航、日记月历和只读模式，完成七主题与响应式样式。
5. **全项目审计与有证据的优化**：只处理经复现或基准确认的问题，记录延后项。
6. **全量验收与发行重建**：更新需求、数据库模型说明、接口清单、用户指南和变更记录，运行全套测试并重建两个 EXE。

提交建议拆为三个可回退主题，并在一次最终批准下选择性提交：

1. `feat(life-os): add habit and health reports`
2. `fix(life-os): refine daily workflows and read-only journal history`
3. `test(life-os): audit data integrity and performance`

如果实现过程中未发生独立性能改动，第三项可以并入第二项；不得为了满足提交数量制造无意义拆分。
